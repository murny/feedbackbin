<objective>
Add ADMN-03 D-10: the signed per-idea unwatch link in every notification email footer + the one-click POST endpoint that verifies the token and toggles the Watch row to `watching: false`. The endpoint MUST work without an authenticated session (recipients click the link from any browser) and MUST be POST-only to defeat email-client prefetch (T-06-01 + T-06-03).

Purpose: D-10 mandates CAN-SPAM-friendly one-click unsubscribe in every notification email. The Rails primitive `Rails.application.message_verifier(:watch_unsubscribe)` (precedent at app/controllers/concerns/authentication/via_magic_link.rb:72-74) handles signing, expiration, and base64 — no hand-rolled crypto (RESEARCH "Don't Hand-Roll" line 727). T-06-03 mitigation: identical responses for invalid/expired/missing tokens to prevent enumeration.

Output: New controller + 2 views + helper + token-generation footers in both mailers (HTML and text) + route + i18n keys + dedicated controller test file.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Email link click → HTTP request | Recipient's email client → public Internet → Rails app; token is the ONLY auth signal (allow_unauthenticated_access skips session check) |
| Recipient's browser → /unsubscribe/destroy_by_token | POST-only endpoint; token in request body OR query string |
| Token → Rails.application.message_verifier(:watch_unsubscribe) | HMAC-SHA256 signed (Rails default); expires_in: 30.days enforced |
| message_verifier output → Watch lookup | Three-field scoped find: `Watch.find_by(id:, user_id:, idea_id:)` requires all three to match a real row |
| Watch.update! → DB write | Single column update (`watching: false`); no cascading side effects |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-01 | Tampering | Signed unwatch token replay / forgery | mitigate | `Rails.application.message_verifier(:watch_unsubscribe).verified(params[:token])` returns nil on signature mismatch OR expiry — controller renders expired page (HTTP 410) on nil payload. POST-only endpoint (route assertion: `bin/rails routes \| grep unsubscribe \| grep -E '^\s*GET\s'` returns zero lines) prevents GET-prefetch by email clients (Outlook safe-links, anti-phishing scanners). Token replay-after-rewatch is documented as accepted v1 risk per RESEARCH Open Question 1 — the threat model is "spouse opens your email and unsubscribes you," not session hijack. Mitigated for hostile-network case by HTTPS only; ContentSecurityPolicy in Rails 8 default headers; no client-side state. |
| T-06-03 | Information Disclosure | Email enumeration via unsubscribe response shape | mitigate | Controller renders the SAME `expired` template with HTTP 410 Gone for ALL of: invalid signature, expired token, valid token but missing watch row. Test "POST destroy_by_token with valid token but missing watch renders expired" asserts this identical-response invariant. An attacker brute-forcing watch_ids cannot distinguish "watch exists" from "watch does not exist" because all three branches return the same status code, template, and content. |
| T-06-04 | Information Disclosure | Internal-comment leakage via mailer footer | mitigate | The footer is added to BOTH mailer views, BUT the Notifier::CommentEventNotifier#recipients filter (plan 06-02 Task 2 + Phase 3 SUMMARY) already prevents non-staff watchers from receiving any IdeaCommentMailer dispatch when the comment is internal — so internal comments cannot leak via the footer link. This plan adds nothing that bypasses that filter; the footer is purely the unsubscribe affordance for already-permitted recipients. |
| T-06-US-01 | Spoofing | Token forgery to unsubscribe another user | mitigate | Token payload includes `user_id` AND `idea_id` redundantly with `watch_id`; controller does `Watch.find_by(id:, user_id:, idea_id:)` — all three must match a real row. A forger would need the message_verifier secret (Rails secret_key_base) which lives only on the server. RESEARCH Focus 6 line 410 confirms defense-in-depth. |
| T-06-US-02 | Denial of Service | Mass-unsubscribe via leaked tokens | accept | If a user's email is fully compromised, the attacker has worse capabilities than unsubscribing. Email-account-compromise is out of scope for application-layer threat model. Per RESEARCH Open Question 1 + Pitfall 4. |
| T-06-US-03 | Tampering | URL parameter exposure of signed token in referer headers | mitigate | The token travels in the POST request body (via `button_to`-shape form) on submit, NOT in URL.
